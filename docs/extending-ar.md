# دليل التعديل والتوسعة

هذا الدليل يجاوب على سؤال واحد: **"أريد أغيّر شيئاً — من وين أبدأ؟"**

كل وصفة هنا مكتوبة خطوة بخطوة، مع الملفات بالضبط، ومع طريقة التأكد أن
التعديل اشتغل. المبدأ العام في المشروع كله:

> كل معلومة لها **مكان واحد**. إذا لقيت نفسك تعدّل نفس القيمة بملفين، فهذا
> خطأ في المعمارية مو في أسلوبك — بلّغ عنه بدل ما تكرّره.

قبل أي تعديل وبعده:

```bash
pnpm check      # typecheck + lint + format + tests + build
```

هذا الأمر هو البوابة. إذا مرّ، تعديلك ما كسر شيئاً. وإذا فشل، رسالة الخطأ
تسمّي الملف والسطر والحل — مكتوبة بهذا الشكل عن قصد.

---

## 1. تغيير نص ظاهر في الموقع

**المكان:** `messages/ar.json` و `messages/en.json`

النصوص كلها في هذين الملفين، ولا يوجد نص عربي مكتوب داخل أي component.

1. دوّر على النص في `messages/ar.json`.
2. غيّره.
3. غيّر مقابله في `messages/en.json`.

**الخطوة 3 ليست اختيارية.** الملفان لازم يحتويان **نفس المفاتيح بالضبط**، وهناك
اختبار يفشل إذا زاد مفتاح في ملف ونقص في الثاني — لأن المفتاح الناقص يظهر
للزبون كنص خام مثل `nav.offers` بدل الكلمة.

### إضافة نص جديد

أضف المفتاح في الملفين، ثم اقرأه في الـ component:

```tsx
// Server Component
const t = await getTranslations('nav');
<span>{t('offers')}</span>;

// Client Component
const t = useTranslations('nav');
```

المفتاح الأول (`'nav'`) هو الـ namespace، والموجود منها:
`brand`, `nav`, `common`, `home`, `product`, `cart`, `auth`, `validation`,
`empty`, `error`, `a11y`, `footer`, `catalogue`.

## 2. تغيير الألوان أو المسافات أو الحواف

**المكان:** `app/globals.css` داخل بلوك `@theme` — ولا مكان غيره.

```css
@theme {
  --color-primary: #e11b22; /* غيّر هنا فقط */
  --radius-card: 0.75rem;
  --aspect-product: 4 / 5;
}
```

التغيير ينطبق على الموقع كله فوراً، لأن كل component يستعمل الـ token
(`bg-primary`, `rounded-card`) ولا يكتب اللون بنفسه.

> **انتبه للصيغة.** Tailwind 4 يكتب الـ token هكذا: `rounded-card`,
> `shadow-card`, `accent-primary`. الصيغة القديمة `rounded-[--radius-card]`
> من Tailwind 3 وتُنتج `border-radius: --radius-card` — قيمة غير صالحة
> يتجاهلها المتصفح بصمت، فتختفي الحواف كلها بلا أي خطأ. حصل هذا فعلاً في
> ١٥٩ موضعاً، ويمنعه الآن اختبار في `tests/architecture.test.ts`.

**ممنوع** تكتب `#e11b22` داخل أي ملف في `app/` أو `components/` أو `features/`.
هناك اختبار يمنعها، ورسالته تسمّي الملف والسطر.

> اللون الأحمر `--color-primary` مخصّص لثلاثة أشياء فقط: زر الشراء، سعر
> التخفيض، والحالة النشِطة. إذا صار لون خلفيات وعناوين، يفقد معناه ويصير
> الزبون ما يعرف وين يضغط.

### إضافة لون جديد

أضفه في `@theme` بنفس النمط:

```css
--color-info: #1d4ed8;
--color-info-soft: #eff6ff;
```

Tailwind يولّد `bg-info` و `text-info` تلقائياً. لا يحتاج `tailwind.config.js` —
غير موجود أصلاً في Tailwind 4.

## 3. إضافة رابط في القائمة أو الفوتر

**المكان:** `config/nav.ts` — ملف واحد للهيدر والقائمة الجانبية والفوتر.

```ts
export const PRIMARY_NAV: readonly NavLink[] = [
  { href: '/products?type=phone', labelKey: 'phones' },
  { href: '/offers', labelKey: 'offers' },
  { href: '/blog', labelKey: 'blog' }, // ← الجديد
];
```

`labelKey` هو مفتاح داخل namespace الـ `nav`، مو نص. يعني لازم تضيف
`"blog"` في `messages/ar.json` و `messages/en.json` (وصفة رقم 1)، وبهذا
الرابط يصير مترجَم بحكم التصميم لا بحكم الانتباه.

القوائم الأربع:

| الثابت           | يظهر في                                         |
| ---------------- | ----------------------------------------------- |
| `PRIMARY_NAV`    | الهيدر (شاشة كبيرة) + القائمة الجانبية (موبايل) |
| `SECONDARY_NAV`  | أسفل القائمة الجانبية فقط                       |
| `HEADER_ACTIONS` | أيقونات يمين الهيدر (السلة، المفضلة، الحساب)    |
| `FOOTER_NAV`     | أعمدة الفوتر                                    |

## 4. إضافة صفحة جديدة

مثال: صفحة `/ar/about`.

1. أنشئ `app/[locale]/(storefront)/about/page.tsx`:

```tsx
import { getTranslations, setRequestLocale } from 'next-intl/server';
import type { Locale } from '@/i18n/routing';

export default async function AboutPage({
  params,
}: {
  params: Promise<{ locale: Locale }>;
}) {
  const { locale } = await params;

  // بدون هذا السطر، الصفحة وكل ما تحتها تخرج من الـ static rendering
  // وتصير dynamic بصمت — بدون أي رسالة خطأ.
  setRequestLocale(locale);

  const t = await getTranslations('about');
  return <main className="container-page py-12">{t('title')}</main>;
}
```

2. أضف نصوصها في `messages/ar.json` و `messages/en.json`.
3. أضف رابطها في `config/nav.ts` (وصفة رقم 3).

الصفحة تشتغل على `/ar/about` و `/en/about` مباشرة — التوجيه حسب اللغة
يتكفّل به `i18n/` ولا يحتاج أي إعداد لكل صفحة.

**انتبه:** لا تضع منطق أعمال داخل `app/`. هذا المجلد للتوجيه والتركيب فقط.
المنطق يروح إلى `server/services/` والاستعلامات إلى `server/queries/`، لأن
ما داخل `app/` لا يمكن اختباره بدون تشغيل Next ولا يمكن للوحة التحكم أن
تعيد استعماله لاحقاً. هناك اختبار ينبّه إذا صار ملف route طويلاً بشكل يدل
على أنه يخبّئ منطقاً.

## 4.5 إضافة منتج جديد (من لوحة التحكم — بدون كود)

**الرابط:** `/ar/admin/products` ← زر **منتج جديد**.

### الخطوات

1. **الأساسيات** — اكتب اسم المنتج بالعربي والإنكليزي. الرابط (slug) يتولد
   تلقائيًا من الاسم الإنكليزي.
2. **التصنيف** — اختر نوع المنتج والماركة والتصنيف.
3. **المواصفات** — انتبه هنا: **الحقول تتغير حسب نوع المنتج اللي اخترته**.
   اختر "هاتف" وتطلع لك مواصفات الهواتف، اختر "ملحق" وتتبدل كلها. هذي مو
   مكتوبة بالكود — جايه من قاعدة البيانات (وصفة رقم 5 و 6).
4. **الخيارات** — مثل الذاكرة واللون. عرّف الخيار وقيَمه أول.
5. **النسخ** — بعد ما تعرّف الخيارات، اضغط **ولّد كل التركيبات** وراح تتولد
   كل النسخ لوحدها مع SKU جاهز. حدد سعر كل نسخة.
6. **الصور** — شوف تحت.
7. **العرض بالمتجر** — أشّر **منشور** حتى يظهر للزبائن. بدونها يضل مسودة.
8. اضغط **أنشئ المنتج**.

### الصور

**الطريقة الأولى — زر "ارفع صورة"** (يحتاج تهيئة مرة وحدة، شوف §4.6 تحت).
تختار الصورة من جهازك، تنرفع لـ Supabase Storage، والرابط ينكتب لوحده.

**الطريقة الثانية — ملف داخل المشروع** (بدون أي تهيئة):

1. حط ملف الصورة داخل مجلد `public`، مثلاً: `public/products/galaxy-s24.jpg`
2. بحقل مسار الصورة اكتب: `/products/galaxy-s24.jpg`

> **ملفات SVG مرفوضة عمدًا** — ملف SVG يكدر يحمل كود يشتغل بمتصفح الزبون.
> والرفض **مبني على محتوى الملف مو على اسمه**: لو غيّرت اسم ملف SVG لـ
> `.jpg` بعده ينرفض. استعمل JPG أو PNG أو WebP أو AVIF.

> **الروابط الخارجية ما تشتغل** (صورة من موقع ثاني) — مسموح بس ملفات مجلد
> `public` وملفات Supabase Storage مالتك. هذا مقصود: أي مصدر جديد ينضاف
> بوعي داخل `next.config.ts`.

### تعديل منتج موجود

نفس الفورم. اضغط اسم المنتج من القائمة.

**شغلتين مهمات وقت التعديل:**

- **تغيير الرابط (slug) يكسر أي رابط قديم** للمنتج — عند الزبائن وبجوجل.
  غيّره بس إذا مضطر.
- **إذا حذفت نسخة (variant) كانت انباعت سابقًا، ما تنحذف — تنطفي بس.**
  السبب: الفواتير القديمة معلّقة بيها. اللوحة تخبرك بعدد النسخ اللي انطفت.

### إخفاء منتج بدل حذفه

من القائمة، زر **اسحب من المتجر**. هذا **يرجع** بأي وقت، والحذف لا.

**شغلة تنتبه لها:** إذا سحبت منتج من المتجر وكان محفوظ عند زبائن بقائمة
الرغبات، الكارت يختفي من قائمتهم — بس **ما ينحذف من قائمتهم**. تظهر لهم جملة
تكَول "اكو منتجات محفوظة مو معروضة حالياً". يوم ترجّعه للعرض، يرجع يبين
مكانه. أما **الحذف النهائي** فيشيله من قوائم الرغبات كلها ونهائياً.

### الحذف

من داخل صفحة المنتج، تحت، بقسم "منطقة الخطر".

**إذا المنتج انباع ولو مرة وحدة، الحذف ينرفض** — والزر ما يظهر أصلاً. هذا
مقصود: الحذف يقطع علاقة الفواتير القديمة بالمنتج، والفاتورة تضل تظهر طبيعية
فما تنتبه أن اكو شي انكسر. استعمل "اسحب من المتجر".

## 4.6 تهيئة رفع الصور (مرة وحدة بس)

بدون هاي الخطوة الموقع يشتغل عادي — بس زر "ارفع صورة" يطلع لك رسالة إنه مو
مهيّأ، وتضل تكتب مسارات الصور يدويًا (§4.5).

**الـ bucket جاهز مسبقًا** باسم `product-images` على مشروعك بـ Supabase:
عام للقراءة، الحد الأقصى ٨ ميغابايت، ويقبل JPG و PNG و WebP و AVIF بس.

باقي عليك تجيب قيمتين وتحطهن بملف `.env`:

### ١. رابط المشروع

Supabase → مشروعك → **Project Settings** → **Data API** → انسخ **Project URL**.
شكله: `https://xxxxxxxx.supabase.co` — **بدون** `/` بالآخر.

```
SUPABASE_URL="https://xxxxxxxx.supabase.co"
```

### ٢. المفتاح السري

Supabase ← **Project Settings** ← **API keys**.

اكو نظامين للمفاتيح، وشنو تشوف يعتمد على عمر مشروعك:

| اللي تشوفه بالصفحة                  | انسخ منه                                                 |
| ----------------------------------- | -------------------------------------------------------- |
| **Secret keys** (النظام الجديد)     | المفتاح اللي يبدي بـ **`sb_secret_`** — اضغط 👁️ حتى يظهر |
| تبويب **Legacy anon, service_role** | المفتاح المسمّى **`service_role`**                       |

**الاثنين يشتغلون** — المتجر يتعامل معهن سوا.

> ❌ **لا تاخذ** `sb_publishable_` ولا `anon` — هذي مفاتيح عامة، ما عندها
> صلاحية رفع، والفحص راح يرفضها.

```
SUPABASE_SERVICE_ROLE_KEY="الصق-المفتاح-هنا"
SUPABASE_STORAGE_BUCKET="product-images"
```

> ### ⚠️ هذا المفتاح خطير — اقرأ هذي الفقرة
>
> مفتاح `service_role` **يتجاوز كل قيود الحماية** بمشروعك. أي واحد يحصل عليه
> يكدر يقرا ويعدل ويمسح **كل** بياناتك.
>
> - لا تحطه بأي مكان يوصل للمتصفح، ولا تسميه `NEXT_PUBLIC_...`
> - لا ترفعه للكيتهاب إطلاقًا — ملف `.env` محمي بـ `.gitignore` مسبقًا
> - لا تلصقه بأي دردشة ولا ترسله لأي شخص
> - إذا تسرب: Supabase → API keys → **Reset** فورًا
>
> بالكود، هذا المفتاح ينقرا بمكان واحد بس (`server/services/admin-storage.ts`)
> والملف مقفول على السيرفر. **المتصفح ما يشوف Supabase أصلاً** — الصورة تنرسل
> للموقع، والموقع يفحصها ويرفعها. لو المتصفح رفع مباشرة لـ Supabase، جان صار
> الفحص نصيحة يكدر أي واحد يتجاوزها.

### ٣. تأكد أن المفاتيح زبطت

```bash
pnpm check:services
```

هذا الأمر **يرفع ملف تجريبي فعلاً ويمسحه** — يعني ما يكتفي بالتأكد أن القيمة
موجودة، يتأكد أنها تشتغل. وإذا اكو غلط، يقول لك بالضبط شنو:

| الرسالة                 | المشكلة                              |
| ----------------------- | ------------------------------------ |
| `المفتاح مرفوض`         | نسخت مفتاح `anon` بدل `service_role` |
| `ماكو bucket`           | اسم الـ bucket غلط                   |
| `ما كدرنا نوصل للسيرفر` | `SUPABASE_URL` غلط أو ماكو إنترنت    |

> **الناتج آمن للمشاركة** — المفاتيح تظهر مخفية (`eyJhb...x9Qk`)، فتكدر ترسل
> لي الناتج إذا احتجت مساعدة، **بس لا ترسل الملف `.env` نفسه أبدًا**.

### ٤. أعد تشغيل الموقع

```bash
pnpm dev
```

افتح أي منتج ← قسم الصور ← **ارفع صورة**.

## 5. إضافة مواصفة جديدة لمنتج

مثال: تريد تضيف "مقاومة الغبار" للهواتف.

**كلها من لوحة التحكم. ما يحتاج كود ولا `pnpm db:seed`.**

1. **المواصفات** ← **مواصفة جديدة**
2. املأ:
   - **التسمية بالعربي**: مقاومة الغبار
   - **التسمية بالإنكليزي**: Dust resistance
   - **المفتاح**: يتولد تلقائياً من الاسم الإنكليزي (`dust_resistance`)
   - **نوع القيمة**: نص / رقم صحيح / رقم عشري / نعم-لا / اختيار من قائمة
   - **الوحدة** (اختياري): تظهر بعد القيمة — GB، mAh، إنش
   - **يستعمل كفلتر**: إذا تريدها تظهر بفلاتر الكتالوك
3. **حفظ**
4. **أنواع المنتجات** ← افتح "هاتف" ← تحت **المواصفات** اضغط
   **+ مقاومة الغبار** ← **حفظ**

خلص. افتح أي هاتف من **المنتجات** وراح تلكَه خانة جديدة اسمها "مقاومة الغبار".

### إذا اخترت "اختيار من قائمة"

تظهر لك خانات **الخيارات**. كل خيار له:

- **القيمة** — تنخزن وتظهر بالرابط. حروف إنكليزية صغيرة و `_` فقط (`ip68`)
- **التسمية بالعربي** و **بالإنكليزي** — هذا اللي يشوفه الزبون

### شغلتين مهمات

**نوع القيمة ما يتغيّر بعد ما تنخزن قيم.** المشروع يرفض التغيير ويكولك كم
قيمة مخزونة. السبب: القيمة تنخزن بعمود يعتمد على النوع — رقم بعمود الأرقام،
نص بعمود النصوص. لو تغيّر النوع، كل القيم القديمة تبقى بالعمود الغلط: موجودة
بقاعدة البيانات، ومختفية من صفحة المنتج، وما تنصلّح بأي تعديل لاحق. الحل:
سوّي مواصفة جديدة.

**شيل مواصفة من نوع ≠ حذف القيم.** إذا شلت "مقاومة الغبار" من نوع "هاتف"،
الخانة تختفي من الفورم بس القيم المحفوظة تبقى — ترجع لو رجّعت المواصفة.
أما **حذف** المواصفة نفسها فمرفوض ما دامت مستعملة بأي منتج.

## 6. إضافة نوع منتج جديد (لابتوب، سماعات، أي شيء)

هذا هو السبب الأساسي وراء تصميم قاعدة البيانات بهذا الشكل: المتجر يبيع
"كل شيء" لاحقاً **بدون إعادة كتابة**.

**وكلها من لوحة التحكم.**

1. سوّي المواصفات اللي يحتاجها النوع (وصفة رقم 5) — وأعِد استعمال الموجودة:
   `ram_gb` و `storage_gb` مشتركة مع الهواتف، لا تكرّرها
2. **أنواع المنتجات** ← **نوع جديد**
3. املأ:
   - **الاسم بالعربي**: لابتوب
   - **الاسم بالإنكليزي**: Laptop
   - **المفتاح**: يتولد تلقائياً (`laptop`) — وهو اللي يظهر بالرابط
     `?type=laptop`، فما يتغيّر بعد الحفظ
   - **الأيقونة** (اختياري): اسم أيقونة من lucide، مثلاً `Laptop`
4. تحت **المواصفات** اضغط على كل مواصفة يسألها النوع. علّم **إجباري** على
   اللي ما يصير منتج بدونها، ورتّبهن بأسهم ↑ ↓ — نفس الترتيب يظهر بجدول
   المواصفات بصفحة المنتج
5. **حفظ**

الآن `/ar/products?type=laptop` يشتغل، والفلاتر تظهر حسب مواصفات اللابتوب،
وصفحة المنتج تعرض جدول مواصفات اللابتوب — لأن كل هذا مبني من البيانات.

**وإضافة لابتوب فعلي؟** **المنتجات** ← **منتج جديد** ← اختر "لابتوب" من
**نوع المنتج**، وراح تشوف خانات المواصفات تتبدّل قدامك للي اخترتها. ما يحتاج
كود ولا seed بأي خطوة.

**ملاحظة:** لو أردت رابطاً في القائمة الرئيسية للنوع الجديد، أضفه في
`config/nav.ts` مع مفتاح ترجمة (وصفة رقم 3) — هذي الشغلة الوحيدة اللي بعدها
بالكود.

**الحذف مرفوض إذا بيه منتجات.** وقّف النوع بدل ما تحذفه: يختفي من المتجر ومن
قائمة إضافة منتج، ومنتجاته تبقى محفوظة.

## 7. إضافة براند أو قسم

### براند

**البراندات** ← **براند جديد**. املأ الاسم بالعربي والإنكليزي — والرابط
(slug) يتولد لوحده من الاسم الإنكليزي.

**لون الهوية** يُستعمل كنقطة صغيرة فقط — لا يصير خلفية ولا لون زر. هذا اللون
**بيانات في قاعدة البيانات**، وهو الاستثناء الوحيد لقاعدة "ممنوع الألوان خارج
`@theme`": لأنه يختلف من صف إلى صف. تكدر تختاره من مربع الألوان أو تلصق الكود
مباشرة (`#1428A0`).

### قسم

**الأقسام** ← **قسم جديد**. نفس الشي، زائد **القسم الأب** إذا تريده متفرّع —
مثلاً "هواتف الألعاب" تحت "الهواتف". خلّه فارغ إذا تريده قسم رئيسي.

القائمة تعرض الشجرة بإزاحة، فتشوف شنو تحت شنو.

### الحذف بالحالتين

مرفوض إذا بيه منتجات — والرسالة تكولك كم منتج. **وقّفه** بدل ما تحذفه:
يختفي من المتجر ومنتجاته تبقى محفوظة.

والقسم مرفوض حذفه هم إذا تحته أقسام ثانية، لأن حذفه كان راح يرفّع الأقسام
اللي تحته للمستوى الرئيسي بدون ما يكولك — يعني التجميع يضيع بالسكوت.

**وما يصير قسم يكون تحت نفسه** ولا تحت قسم متفرّع منه. القائمة أصلاً ما
تعرضلك هذا الخيار، والخدمة ترفضه مرة ثانية لو وصلها.

## 8. تغيير أرقام الواجهة

**المكان:** `config/ui.ts`

```ts
export const PRODUCTS_PER_PAGE = 25; // منتجات كل صفحة في الكتالوك
export const RAIL_SIZE = 5; // منتجات كل شريط في الرئيسية
export const RELATED_SIZE = 4; // المنتجات المشابهة
export const MOBILE_BUY_BAR_OFFSET = 520; // متى يظهر شريط الشراء
export const RELATED_PRICE_SPREAD = 0.4; // مدى قرب سعر المنتج المشابه
```

`PRODUCTS_PER_PAGE` و `RAIL_SIZE` مربوطان بعدد أعمدة الشبكة (٥ على الشاشة
الكبيرة)، فإذا غيّرت واحداً منهما خلّه من مضاعفات عدد الأعمدة، وإلا ينتهي
الصف الأخير بكارت أو اثنين لوحدهم.

قاعدة هذا الملف: **كل ثابت فيه له مستهلك فعلي.** هناك اختبار يفشل إذا أضفت
ثابتاً ما يستعمله أحد، لأن ملف إعدادات ما أحد يقرأه أسوأ من عدم وجوده —
يبدو كأنه المصدر بينما الرقم الحقيقي مكتوب في مكان ثاني.

الألوان والمسافات والحواف **ليست هنا**؛ مكانها `@theme` (وصفة رقم 2).

## 9. تغيير الأسعار أو أجور التوصيل أو أرقام التواصل

**لا تعدّل الكود.** هذه بيانات تجارية ومكانها قاعدة البيانات:

| المعلومة                             | الجدول           |
| ------------------------------------ | ---------------- |
| أجور التوصيل ومدته لكل محافظة        | `DeliveryRate`   |
| رقم الواتساب، الضمان، معلومات المتجر | `SiteSetting`    |
| أسعار المنتجات                       | `ProductVariant` |

```bash
pnpm db:studio
```

السبب وراء هذا كله: تغيير سعر يجب ألّا يحتاج نشر إصدار جديد من الموقع.

## 9.5 تسجيل الدخول للوحة التحكم

**الرابط:** `/ar/sign-in` — أو اضغط أيقونة الحساب بأعلى الموقع.

### الحسابات الجاهزة

`pnpm db:seed` ينشئ حسابين للتجربة:

| البريد               | الدور      | يشوف شنو                |
| -------------------- | ---------- | ----------------------- |
| `admin@mps.local`    | `ADMIN`    | لوحة التحكم كاملة       |
| `customer@mps.local` | `CUSTOMER` | المتجر فقط، بدون اللوحة |

### كلمة المرور

**مو مكتوبة بأي ملف داخل المشروع** — لأن المستودع عام، وأي كلمة مرور تُكتب
بالكود تصير معروفة للجميع. عندك طريقتين:

**الطريقة الأولى — تختار كلمة المرور بنفسك (المفضّلة):**

1. شغّل:

   ```bash
   pnpm keys
   ```

   يسألك عن «كلمة مرور حسابات التجربة» — اكتبها (8 حروف على الأقل) ويحفظها
   بالملف لوحده. باقي الأسئلة تخطّاها بـ Enter.

   > أو عدّل `.env` بنفسك وأضف السطر: `DEMO_ADMIN_PASSWORD="كلمة-المرور"`

2. شغّل:

   ```bash
   pnpm db:seed
   ```

3. سجّل دخول بـ `admin@mps.local` وكلمة المرور اللي اخترتها.

**الطريقة الثانية — تترك الأمر للنظام:** لا تضيف المتغيّر، وشغّل `pnpm db:seed`.
راح يولّد كلمة مرور عشوائية ويطبعها بالترمنال **مرة واحدة**:

```
demo users: admin@mps.local (ADMIN), customer@mps.local (CUSTOMER)
password for both: xK7pQm2vNbTr
```

انسخها فورًا. إذا ضاعت، ارجع للطريقة الأولى — ما تحتاج تمسح شيء، لأن
`db:seed` يحدّث ولا يحذف.

### بعد تسجيل الدخول

- حساب `ADMIN` أو `STAFF` → يفتح `/ar/admin`.
- حساب زبون عادي → يرجع للصفحة الرئيسية، وهذا صح مو خطأ.

### لو ما اشتغل

| الحالة                           | السبب الأكثر شيوعًا                                      |
| -------------------------------- | -------------------------------------------------------- |
| "بيانات الدخول غير صحيحة"        | ما شغّلت `pnpm db:seed` بعد، فالحساب أصلاً ماكو          |
| الصفحة تقبل الدخول وترجعك للفورم | `BETTER_AUTH_URL` بـ `.env` مو نفس العنوان اللي تفتح منه |
| يطلع خطأ قاعدة بيانات            | شوف §9.9 تحت                                             |

> **مهم قبل الإطلاق:** هذين الحسابين **للتجربة فقط**، و `pnpm db:seed` يرفض
> يشتغل على `NODE_ENV=production` — يعني ما راح يصيرون موجودين على المتجر
> الحقيقي. إنشاء حسابات الموظفين من اللوحة نفسها يجي بالمرحلة الخامسة.

## 9.6 تفعيل تسجيل الدخول بحساب Google

بدون هاي الخطوة الموقع يشتغل عادي — صفحة الدخول تعرض الإيميل وكلمة المرور بس،
وما يظهر زر Google إطلاقًا.

### الخطوات من Google Cloud

1. افتح [console.cloud.google.com](https://console.cloud.google.com) وسوّي
   مشروع جديد (أو اختر واحد موجود).
2. من القائمة: **APIs & Services** ← **OAuth consent screen**
   - نوع المستخدم: **External**
   - املأ اسم التطبيق وبريد الدعم — هذا اللي يشوفه الزبون بشاشة Google.
3. **APIs & Services** ← **Credentials** ← **Create credentials** ←
   **OAuth client ID**
   - Application type: **Web application**
   - تحت **Authorised redirect URIs** أضف بالضبط:

     ```
     http://localhost:3000/api/auth/callback/google
     ```

     ولما تنشر الموقع أضف نسخة ثانية بالرابط الحقيقي:

     ```
     https://your-domain.com/api/auth/callback/google
     ```

   > **لازم يكون مطابق حرف بحرف** — نفس `http`/`https`، نفس المنفذ، وبدون `/`
   > زيادة بالآخر. أي اختلاف و Google يرفض ويعطي
   > `redirect_uri_mismatch`.

4. انسخ **Client ID** و **Client secret** وحطهن بملف `.env`:

```
GOOGLE_CLIENT_ID="....apps.googleusercontent.com"
GOOGLE_CLIENT_SECRET="الصق-السر-هنا"
```

5. تأكد أن المفاتيح زبطت:

```bash
pnpm check:services
```

هذا يسأل Google مباشرة إذا الـ ID والـ Secret زوج صحيح — بدون ما يسجّل دخول
ولا يصدر أي توكن. ويطبع لك رابط الرجوع المطلوب حرف بحرف حتى تنسخه.

| الرسالة                | المشكلة                                     |
| ---------------------- | ------------------------------------------- |
| `Google رفض المفاتيح`  | الـ ID أو الـ Secret غلط، أو من client ثاني |
| `رابط الرجوع مو مسجّل` | ما أضفت الـ redirect URI بـ Google Cloud    |

6. أعد تشغيل الموقع (`pnpm dev`) — زر **تابع بحساب Google** راح يظهر.

> **`GOOGLE_CLIENT_SECRET` سري.** لا ترفعه للكيتهاب ولا تلصقه بأي دردشة.
> `.env` محمي مسبقًا.

### شغلة مهمة: شنو يصير لو الإيميل موجود من قبل؟

مثال: زبون سجّل بـ `ali@gmail.com` وكلمة مرور، وبعدين جا يدخل بـ Google بنفس
الإيميل.

**المتجر ما يربطهن تلقائيًا** — ويعطيه رسالة: "سجّل دخول بكلمة المرور أولاً".

**ليش؟** لأن التحقق من البريد الإلكتروني مطفي حاليًا (ما بعد اكو مزوّد إيميل).
يعني أي واحد يكدر يسجّل بإيميل **مو إله**. لو ربطنا تلقائيًا، جان صاحب
الإيميل الحقيقي لما يدخل بـ Google يلگى نفسه **داخل حساب شخص ثاني** — وما
ينتبه، لأن كلشي يبين طبيعي.

الحماية مكتوبة صراحةً بـ `server/auth/auth.ts` تحت
`accountLinking.requireLocalEmailVerified`. **لا تشيلها** حتى بعد ما نفعّل
التحقق من البريد — تضل صحيحة بالحالتين.

## 9.7 تسوّي كود خصم (كوبون)

من لوحة التحكم → **كوبونات الخصم** → **كوبون جديد**.

### الكود

حروف إنكليزية وأرقام و`-` و`_` بس. الزبون يكدر يكتبه بأي حالة أحرف وبمسافات
زايدة — ينتنظّف قبل ما ينقارن.

### نوع الخصم

- **نسبة مئوية** → تكتب رقم من 1 لـ 100. تكدر تحط **أقصى خصم** حتى النسبة ما
  تكبر بطلب كبير. مثال: 15% مع سقف 20,000 د.ع — طلب بـ 600,000 ينخصم 20,000
  مو 90,000.
- **مبلغ ثابت** → تكتب المبلغ بالدينار.

**الكسور تنزل للأسفل دائماً.** 15% من 68,000 = 10,200 بالضبط، وإذا طلعت كسور
ناخذ الأقل — الزبون ما يدفع أكثر من الخصم المعلن.

### الحدود — هذي اللي تحميك

| الحقل                     | شنو يسوي                                         |
| ------------------------- | ------------------------------------------------ |
| **أقل مبلغ للطلب**        | تحت هذا المبلغ الكود ما يشتغل                    |
| **عدد الاستخدامات الكلي** | كم مرة يُستعمل الكود بالمجموع. فاضي = بلا حد     |
| **لكل حساب**              | كم مرة للحساب الواحد                             |
| **مدة الصلاحية**          | من تاريخ لتاريخ. برا المدة ما يشتغل حتى لو مفعّل |
| **مفعّل**                 | مفتاح إطفاء فوري، بدون ما تحذف شي                |

**انتبه على "لكل حساب":** ينطبق على الزبون **المسجّل دخول بس**. الزائر اللي
يشتري بدون حساب ماكو له حساب ينحسب عليه، فهو يكدر يستعمله أكثر من مرة. اللي
يحدد كلفتك فعلياً هو **عدد الاستخدامات الكلي** — خلّيه مكتوب دائماً إذا الكود
سخي.

### الخصم ينحسب وين؟

**بالسيرفر، من الكود بس.** المتصفح يرسل الكود، ما يرسل مبلغ — حتى لو أحد عدّل
الصفحة، السعر اللي ينحسب هو سعرنا إحنا. والخصم ينحسب مرتين: مرة لما الزبون
يضغط "طبّق" (هذا بس عرض — ما يستهلك استخدام)، ومرة ثانية جوّة نفس العملية اللي
تكتب الطلب. يعني اللي انعرض واللي انحسب يطلعون من نفس المكان.

### شنو يشوف الزبون لو الكود غلط؟

"الكود غير صحيح أو منتهي" — **نفس الرسالة** للكود اللي ماكو، والموقّف، واللي
خلصت مدته. هذا مقصود: لو نفرّق بينهم، أي واحد يكدر يجرّب أكواد ويعرف شنو
أكوادك ومتى تشتغل. الرسائل اللي تفرّق هي بس اللي تخص طلب الزبون نفسه: "طلبك
أقل من الحد"، "انتهت استخداماته"، "استعملته من قبل".

### الحذف

**ما ينحذف كود انستعمل.** لو انحذف، سجلات الاستخدام تنمسح ويّاه بينما الخصم
يضل مكتوب على الطلبات — يعني فلوس ناقصة بالدفاتر وماكو شي يفسّرها. الحل: شيل
علامة **مفعّل**. الكود يوقف فوراً والسجل يبقى.

### تشوف الاستخدام

بالجدول عمود **استُعمل** — ينزاد لحاله مع كل طلب، وما ينتعدل من الشاشة.

### تريد تجرّب قبل ما تسوّي كود مالك؟

`pnpm db:seed` يسوّي كود تجريبي جاهز: **`MPS10`** — خصم ١٠٪ بسقف ٢٥٬٠٠٠ د.ع،
وأقل طلب ٥٠٬٠٠٠ د.ع. اكتبه بصفحة إتمام الطلب وشوف شلون ينزل الإجمالي.

هذا **بيانات تجريبية** مثل المنتجات التجريبية — `pnpm db:seed` يرفض يشتغل على
قاعدة بيانات إنتاج. لو ما تريده موجود، شيل علامة **مفعّل** عنه من لوحة التحكم.

## 9.75 قائمة الرغبات والمقارنة — شنو يلزمك تعرف

الاثنين يشتغلون لحالهم، **ماكو شي تسويه من لوحة التحكم**. بس اكو شغلتين
تنفعك تعرفهن:

### قائمة الرغبات

الزبون يضغط على **القلب** بأي منتج وينحفظ بحسابه. يحتاج **حساب** — لأن
القائمة تتبع الحساب مو المتصفح، حتى يلكاها لو دخل من موبايله. الزائر بلا حساب
يشوف "سجّل دخول حتى تحفظ" بدل زر ما يسوي شي.

**لو سحبت منتج من المتجر** وكان محفوظ عند زبائن: يختفي من قائمتهم بس **ما
ينحذف منها**، وتطلع لهم جملة تفسّر. ترجّعه للعرض، يرجع يبين مكانه.

### المقارنة

الزبون يعلّم على **علامة الميزان** بالكروت — لحد **٤ منتجات** — وتطلع له شريط
تحت بيه زر "قارن". الجدول يقارنهم بالسعر والتوفّر والكفالة وكل المواصفات.

**المواصفات بالجدول تجي من نوع المنتج نفسه.** يعني لو سويت نوع جديد (لابتوب
مثلاً) وربطت له مواصفات (§6)، المقارنة راح تقارن بهذيك المواصفات بدون ما أحد
يكتب كود. نفس الشي اللي يصير بصفحة المنتج وبفورم الإضافة.

- **تقارن أنواع مختلفة؟** يصير، بس أكثر الصفوف راح تطلع فارغة — والصفحة تكَول
  لك هذا صراحةً. مو خطأ، هيك الجدول يطلع لما تقارن موبايل ويّا كيبل.
- **الرابط يتشارك.** الجدول كله محفوظ بالرابط (`?ids=`)، يعني الزبون يكدر
  يرسله لواحد ثاني ويفتح نفس المقارنة. التعليمات نفسها محفوظة بالمتصفح بس،
  فهي **ما تروح ويّاه لموبايله** — بس الرابط يروح.

## 9.76 آراء الزبائن — شلون تشتغل وشنو دورك بيها

من لوحة التحكم → **آراء الزبائن**.

### منو يكدر يكتب رأي؟

**بس الزبون اللي وصله المنتج فعلاً** — يعني عنده طلب حالته **"تم التسليم"**
بهذا المنتج بالضبط. مو أي واحد عنده حساب.

ليش هيك؟ لأن سوّي حساب بمتجرنا ما يكلّف شي (ماكو تحقق بريد لحد الآن)، فواحد
يريد يأذيك يكدر يسوّي عشر حسابات ويغرق صفحة المراجعة بأسرع ما تكدر تقراها.
بهذي القاعدة، **كل رأي بالمتجر من واحد استلم الغرض** — وهذا ينفعك أكثر من عدد
آراء كبير محد يصدّقه.

اللي ما اشترى يشوف سطر يفسّر له السبب، مو فورم يضغطه ويطلع له خطأ.

### شنو دورك؟

**ماكو رأي يوصل صفحة المنتج قبل ما تقراه إنت.** كل رأي جديد يجي لـ **بالانتظار**.

| الزر      | شنو يسوي                                        |
| --------- | ----------------------------------------------- |
| **انشره** | يبين بصفحة المنتج، وينحسب بالمعدّل والنجوم      |
| **ارفضه** | ما يبين لأحد، بس يبقى محفوظ عندك بتبويب "مرفوض" |
| **حذف**   | يمحيه نهائياً                                   |

**متى ترفض ومتى تحذف؟** الرفض للرأي اللي ما تريده ينشر — إعلان، كلام مو بمحله.
الحذف للنص اللي **ما لازم ينخزن أصلاً**: رقم تلفون، عنوان بيت، إساءة لشخص
معيّن. الرفض يرجع، الحذف لا.

### التقييم مو مكان تخفي النقد

الزبون يشوف جملة صريحة قبل ما يكتب: "رأيك ينراجع قبل ما ينشر — هذا حتى نمنع
الإعلانات والإساءة، مو حتى نخفي الرأي السلبي." إذا صرت ترفض كل ٢ نجوم، الجملة
هذي تصير كذبة — والزباين ينتبهون أسرع مما تتصور، وثقتهم بكل الآراء تروح.

### النجوم والمعدّل

ينحسبون **من الآراء المنشورة بس**، ويتعدّلون تلقائياً كل ما تنشر أو ترفض أو
تحذف. المنتج اللي ماكو عنده ولا رأي **ماله تقييم** — مو صفر نجوم. صفر نجوم
يعني كلهم كرهوه، وهذا كلام ما كاله أحد.

### الشغل اللي ينتظرك

تبيّن بالصفحة الرئيسية للوحة التحكم، بمربع **"بالانتظار"** — بنفس مكان الطلبات
الجديدة، ولنفس السبب: واحد كاتب شي وقاعد ينتظر يشوفه.

## 9.8 تكتب مقال "دليل شراء"

من لوحة التحكم → **أدلة الشراء** → **دليل جديد**.

### الحقول المطلوبة

العنوان بالعربي والإنكليزي، والرابط (ينتعبّى تلقائياً من العنوان الإنكليزي)،
والنص باللغتين.

### شلون تكتب النص

ماكو محرر بأزرار — تكتب نص عادي، وثلاث قواعد بس:

```
## هذا يصير عنوان فرعي

هذا سطر عادي، يصير فقرة.

- وهذا يصير نقطة
- وهذا نقطة ثانية
```

**ماكو HTML.** لو لصقت كود أو وسم، ينعرض كنص عادي — مو خطأ، هذا مقصود حتى
ماكو أحد يكدر يحقن شي بصفحة متجرك.

### النشر

- **ما تعلّم "منشور"** → يبقى مسودة، محد يشوفه غيرك.
- **تعلّم "منشور" وتترك التاريخ فاضي** → ينشر هسه.
- **تعلّم "منشور" وتحط تاريخ بالمستقبل** → يبقى مخفي لحد ما يوصل التاريخ.
  هيك تكدر تكتب ٣ مقالات بيوم وحد وتخليهم يطلعون واحد واحد.

### وين يظهر

بصفحة **دليل الشراء** بالمتجر، **فوق** المداخل الجاهزة (حسب النوع، حسب
البراند، حسب الميزانية). المداخل تبقى مكانها — يعني حتى لو ما عندك ولا مقال،
الصفحة تضل شغّالة وما تطلع فارغة.

كل مقال يصير عنده رابط خاص: `/ar/guides/<الرابط>` و`/en/guides/<الرابط>` —
نفس الرابط باللغتين، وينضاف تلقائياً لـ sitemap حتى يلكاه جوجل.

### انتبه

**لا تغيّر الرابط بعد النشر.** أي واحد شارك المقال أو جوجل فهرسه، الرابط
القديم راح ينكسر.

## 9.9 الموقع يطلع خطأ: "Database not ready"

هذا أكثر خطأ راح تشوفه، وغالبًا **مو خطأ بالكود** — قاعدة البيانات مو شغّالة.

الرسالة نفسها تقول لك السبب والحل. أهم الحالات:

| الكود   | شنو صار                                   | الحل                                          |
| ------- | ----------------------------------------- | --------------------------------------------- |
| `P1001` | PostgreSQL مو شغّال أو المنفذ غلط         | شغّله (تحت)، أو صحّح المنفذ بـ `DATABASE_URL` |
| `P1000` | اسم المستخدم أو كلمة المرور غلط           | صحّح `DATABASE_URL` بملف `.env`               |
| `P1003` | قاعدة البيانات المذكورة ماكو              | `pnpm setup`                                  |
| `P2021` | جدول ناقص — الـ migrations ما انطبّقت     | `pnpm db:deploy` وبعدها `pnpm db:seed`        |
| `P2022` | عمود ناقص — الـ schema سبق قاعدة البيانات | `pnpm db:migrate`                             |

### شلون تشغّل PostgreSQL

**ويندوز** — الأكثر شيوعًا: الخدمة ما اشتغلت بعد إعادة تشغيل الجهاز.

1. اضغط `Win + R` واكتب `services.msc` ثم Enter.
2. دوّر على `postgresql-x64-16`.
3. كليك يمين ← **Start**.
4. حتى ما تتكرر: كليك يمين ← Properties ← Startup type ← **Automatic**.

**لو تستعمل Docker:**

```bash
docker compose up -d
```

**لينكس:**

```bash
sudo service postgresql start
```

### تأكد أن الاتصال صار

```bash
pnpm db:studio
```

إذا فتح وشفت الجداول، قاعدة البيانات شغّالة. أعِد تحميل الموقع.

> **ملاحظة مهمة:** الخطأ يظهر عادة على الصفحة الرئيسية عند
> `product.findMany()` — لأنها أول استعلام ينفّذ. **المشكلة مو بهذا السطر**؛
> هو بس أول واحد لمس قاعدة البيانات.

## 9.10 تشغيل الاختبارات قبل ما تنشر

### الأمر الأساسي

```
pnpm check
```

هذا يفحص الأنواع، وقواعد الكود، والتنسيق، ويشغّل كل الاختبارات، وبالآخر يبني
الموقع. إذا طلع أخضر — تكدر تنشر.

### اختبارات المتصفح (e2e)

هذي منفصلة، لأنها تحتاج متصفح حقيقي يفتح الموقع **المبني** ويشتري منه فعلاً.
مرّة وحدة بس، نصّب المتصفح:

```
npx playwright install chromium
```

وبعدين، كل مرة تريد تشغّلها — **كل أمر بسطر لوحده**، لأن PowerShell عندك
ما يفهم `&&`:

```
pnpm build
pnpm test:e2e
```

### شرط قبل ما تشتغل

الاختبارات تسجّل دخول للوحة التحكم، فلازم تعرف كلمة المرور. تأكد أن
`DEMO_ADMIN_PASSWORD` مكتوبة بـ `.env` (بـ `pnpm keys`)، وشغّل:

```
pnpm db:seed
```

مرة وحدة، حتى تنكتب نفس الكلمة بقاعدة البيانات. إذا ما سويتها، الاختبار
راح يوقف ويكلك نفس هذا الكلام.

### شنو تفحص بالضبط

زبون يشتري هاتف ويتابع طلبه · متصفح ثاني ما يكدر يفتح طلب مو مالته · صفحة
التتبّع تجاوب نفس الجواب للرقم الغلط وللطلب اللي ما موجود · تسجيل الخروج
يمسح أثر الطلب من المتصفح · سحب منتج من المتجر يخليه يختفي من الصفحات ·
حقول المواصفات تتغيّر حسب نوع المنتج · شريط الشراء بالموبايل ما يغطّي
الفوتر · ماكو صفحة تنزلق يمين ويسار.

### لو طلع خطأ "port in use"

يعني عندك نسخة من الموقع شغّالة من قبل. سكّرها (`Ctrl + C` بالنافذة اللي
شغّالة بيها) وأعد الأمر. هذا مقصود: لو الاختبارات استعملت النسخة القديمة،
راح تفحص بناءً قديم وتكلك "كلشي تمام" وهو مو تمام.

## 10. تعديل قاعدة البيانات نفسها

إذا كان التعديل **حقيقياً** في البنية (جدول جديد، علاقة جديدة) — وليس مواصفة
أو نوع منتج، لأن هذين بيانات:

1. عدّل `prisma/schema.prisma`.
2. أنشئ migration:

```bash
pnpm db:migrate
```

3. إذا كانت هناك قاعدة `CHECK` تحمي المنطق، أضفها يدوياً في ملف الـ SQL
   المتولّد. Prisma لا يعبّر عنها، وهي خط الدفاع الأخير: حتى لو وصل كود فيه
   خطأ إلى الإنتاج، قاعدة البيانات ترفض الصف الخاطئ.

```sql
-- مثال حقيقي من ملف الـ migration الأول:
ALTER TABLE "order_item"
  ADD CONSTRAINT "order_item_line_total_consistent"
    CHECK ("lineTotalIqd" = "unitPriceIqd" * "quantity");
```

> انتبه لأسماء الأعمدة: Prisma يحافظ على `camelCase` داخل قاعدة البيانات،
> بينما أسماء الجداول مُعاد تسميتها بـ `@@map` إلى `snake_case`. اكتب الاسم
> كما هو في `prisma/schema.prisma` بالضبط.

4. في الإنتاج **دائماً** `pnpm db:deploy`، أبداً `db:migrate`.

## 10.5 إذا أضفت شي من موقع ثاني (فيديو، خريطة، أداة)

الموقع يرسل هيدر اسمه **Content-Security-Policy** يمنع المتصفح من تحميل أي شي
من نطاق مو مكتوب بالقائمة. هذا مقصود: لو انحقن سكربت بالصفحة، المتصفح يرفضه.

بس معناها إذا أضفت iframe أو صورة من نطاق جديد — خريطة، أداة دردشة، فيديو من
مكان غير يوتيوب — **راح ينحجب بصمت**. الصفحة تشتغل، بس المربّع يطلع فاضي وماكو
رسالة خطأ واضحة.

**الحل**: افتح `lib/security-headers.ts` وضيف النطاق للسطر المناسب:

- صورة من نطاق جديد → `img-src`
- iframe من نطاق جديد → `frame-src`

وبعدها شغّل `pnpm test:e2e` — عدنا اختبار يفتح كل الصفحات ويسأل المتصفح
"شنو رفضت؟"، فإذا نسيت نطاق، الاختبار يكلك.

**ملاحظة**: نطاقات يوتيوب مكتوبة مرة وحدة بـ `lib/video.ts` والهيدر يقراها من
هناك، فلا تكتبها مرتين.

## 11. الحدود التي يمنعها المشروع تلقائياً

هذه ليست نصائح — هي اختبارات وقواعد lint تفشل فوراً:

| القاعدة                                   | أين تُفرض                                   |
| ----------------------------------------- | ------------------------------------------- |
| مفاتيح الترجمة متطابقة بين اللغتين        | `tests/architecture.test.ts`                |
| ممنوع `ml-` / `mr-` / `left-` / `right-`  | اختبار — استعمل `ms-` `me-` `start-` `end-` |
| ممنوع لون hex داخل الواجهة                | اختبار                                      |
| ممنوع استيراد Prisma داخل component       | اختبار + ESLint                             |
| `lib/` لا تستورد Next ولا `server/`       | اختبار + ESLint                             |
| `components/ui` لا تعرف شيئاً عن المنتجات | اختبار + ESLint                             |
| ممنوع نص عربي مكتوب داخل component        | اختبار                                      |
| ممنوع نص عربي مكتوب داخل اختبار e2e       | اختبار                                      |
| كل دالة إدارية تنادي حارس صلاحيات         | اختبار                                      |
| ممنوع سعر مكتوب داخل الكود                | اختبار                                      |
| كل ثابت في `config/` له مستهلك            | اختبار                                      |
| كل ملف في `server/` يبدأ بـ `server-only` | اختبار                                      |
| ممنوع `any` أو تعطيل الأنواع              | ESLint                                      |

كل رسالة فشل تسمّي **الملف والسطر والحل**، لأن اختباراً يقول "فيه مخالفة"
بس يضيّع وقت أكثر مما يوفّر.

## 12. الأشياء التي لا تُغيَّر بدون موافقة صاحب المشروع

مذكورة كاملة في `CLAUDE.md` القسم 13. أهمها:

- **السعر رقم صحيح بالدينار** (`Int`) — لا Float ولا Decimal ولا فلس.
- **التوفر حالة مو كمية** — `Inventory.status` هو الحقيقة.
- **ممنوع أعمدة خاصة بالهاتف على `Product`** — المواصفات بيانات.
- **الخادم يعيد حساب كل سعر** — العميل ما يرسل مبالغ أبداً.
- **كل النصوص في `messages/`** بعدد مفاتيح متساوٍ.

هذه ليست تفضيلات أسلوب؛ كل واحدة منها تمنع خطأً كلّف المشروع وقتاً من قبل.
